## 対象ファイル
- **repoの `reflect-os/index.html`**。作業前に必ず `git pull`。
- ローカルコピーやダウンロードファイル（index(3).html等）を対象にしない。

## 前提【重要】
- このアプリは単一HTML内のVanilla JavaScriptで動作する。
- **主データはIndexedDB（DB名：ReflectOS7）に保存されている**。localStorageは補助
  （myapps_vision等）にのみ使用。実際のコードを確認して正とすること。
- 既存のログ、テーマ、Lectica、VISION、インポート・エクスポート機能は維持する。
- 最初にコード全体を確認し、現在のデータ構造・描画処理・保存処理を把握したうえで実装する。
- 大規模なフレームワーク移行は行わず、現在の構成とデザインテイストを活かす。

# 改修の目的

現在のReflect OSは、問いと実験を蓄積・閲覧する機能はあるが、
「重要な問いを選ぶ」「問いに実験を紐づける」「実験結果から学びを得る」
「定着した学びを実践原則に昇格する」という探求サイクルがUI上で表現されていない。

Reflect OSを、一覧管理ツールではなく、以下の流れを回すOSへ変更する。

問い → 実験 → 振り返り・学び → 実践原則 → 次の問い・実験

# 最重要方針

1. 左メニューの「問い」と「実験」を「探求ボード」に統合する
2. 問いと実験を独立したデータとして保存する
3. 1つの問いの下に、関連する実験を表示する
4. 重点の問いは最大3件、実験中は最大3件に制限する
5. 候補・重点・完了・原則化を明確に分ける
6. 既存データを失わず、新構造へ移行する
7. スマートフォン表示も維持する
8. **3フェーズに分割し、各フェーズ完了時に動作確認→コミット＆pushする**（後述）

# 左メニュー変更

現在の「問い」「実験」メニューを削除または非表示にし、「探求ボード」へ統合する。

探求ボード内には、次のタブまたはフィルターを設置する。

1. 重点
2. 候補
3. 実践原則
4. 完了

左メニュー全体は、おおむね以下の構成にする。

・ホーム
・ログ
・探求ボード
・Lectica
・検索
・アーカイブ
・VISION設定
・取り込む

既存のアーカイブとの役割が重複する場合は、既存アーカイブをログ・Lectica等を含む
全体アーカイブとして残し、探求ボード内の「完了」は問い・実験の完了一覧として扱う。

# 新しいデータ構造

問いと実験を、ログ内のquestion・nextExp文字列や行番号ではなく、
独立したIDを持つデータとして管理する。

**新データ（questions / experiments / principles）はIndexedDB（ReflectOS7）の
新ストアとして追加する。localStorageに新設しない（二重保存の分裂を作らない）。**

- ストア追加にはDBバージョンアップが必要。onupgradeneededで既存ストア
  （logs/themes/checks/Lectica系）を壊さないこと。
- **DB名は変えない**（過去にDBバージョン競合でReflectOS6→7に改名した経緯がある。
  DB名を変えると既存データが見えなくなる）。

## Question

{
  id: string,
  title: string,
  themeIds: string[],
  status: "candidate" | "focus" | "resolved" | "discarded" | "merged",
  hypothesis: string,
  sourceLogIds: string[],
  mergedIntoId: string | null,
  createdAt: string,
  updatedAt: string,
  completedAt: string | null
}

## Experiment

{
  id: string,
  questionId: string | null,
  title: string,
  themeIds: string[],
  status: "candidate" | "active" | "review" | "complete" | "changed" | "paused" | "discarded" | "principled",
  scene: string,
  observation: string,
  deadline: string,
  result: string,
  learning: string,
  sourceLogIds: string[],
  createdAt: string,
  updatedAt: string,
  completedAt: string | null
}

## Principle

{
  id: string,
  title: string,
  category: "dialogue" | "decision" | "organization" | "self" | "other",
  description: string,
  sourceExperimentIds: string[],
  sourceQuestionIds: string[],
  status: "active" | "archived",
  createdAt: string,
  updatedAt: string
}

フィールド名は既存コードとの整合性を考慮して変更してよいが、
問い・実験・原則を独立管理できる構造にする。

# 移行前スナップショット【必須・移行より先に実装】

初回移行の実行**前**に、IndexedDB全データ＋関連localStorageを1つのJSONにまとめ、
自動ダウンロード（または明示的な保存確認）させること。移行はその後に行う。
理由：過去にデータ消失インシデントがあり、restore guardを整備した経緯がある。
移行という危険な操作に保険なしは不可。

# 既存データの移行

既存のログには、questionとnextExpが複数行の文字列として保存されている。

初回起動時に、新しいquestions・experimentsデータが存在しない場合のみ、
既存ログから自動移行する。

## 問いの移行

各ログのquestionを改行単位で分割し、1行ごとにQuestionを作成する。

・元ログIDをsourceLogIdsに保存
・元ログのthemesをthemeIdsへ引き継ぐ
・既存checksの状態を引き継ぐ

状態変換：important → focus ／ todo → candidate ／ done → resolved ／ skip → discarded

## 実験の移行

各ログのnextExpを改行単位で分割し、1行ごとにExperimentを作成する。

状態変換：doing → active ／ todo → candidate ／ done → complete ／ skip → discarded

## 移行の共通ルール

- 空行・行頭記号（・ - 数字. 等）は除去してから1件化する。
  空文字・記号のみの行からQuestion/Experimentを作らない。
- 複数行で1つの問いを書いていた過去ログが断片化する可能性は許容する
  （全てcandidateに入るため、整理モードの「統合」で後から束ねられる）。
- 移行済みフラグまたはバージョン番号を保存し、同じデータを何度も生成しない（冪等）。
- 既存のログ内question・nextExpは削除せず、過去データとの互換性のため残す。

# 探求ボード：重点画面

重点画面では、重点の問いをカード形式で表示する。

画面上部に以下を表示する。

重点の問い　X / 3
実験中　　　Y / 3

## 問いカードの表示内容

・問い ・関連テーマ ・現在の仮説 ・関連する実験 ・直近の学び ・作成元ログ ・更新日

例：

--------------------------------
相手の人生と会社の未来をどう接続するか？

テーマ：仲間づくり

現在の仮説：
相手の未来を会社に合わせるのではなく、双方の未来の接点を設計する。

実験中 1件
▶ 重要な対話の前に、相手が守りたいものと望む未来を書き出す

直近の学び：
人生応援と経営責任は分離せず設計できる

［実験を追加］［編集］［統合］［解消］
--------------------------------

問いカードはクリックで開閉できるようにする。

# 重点数の制限

重点の問いは最大3件、実験中の実験も最大3件にする。

4件目を重点化または実験中にしようとした場合は、単にエラー表示するのではなく、
現在の3件を表示して、どれを候補へ戻すか選択できるモーダルを表示する。

表示例：

重点の問いは最大3件です。
新しい問いを重点化するには、現在の重点から1件を候補へ戻してください。

○ 問いA
○ 問いB
○ 問いC

［入れ替える］［キャンセル］

# 探求ボード：候補画面

候補画面には以下を表示する。

・問いの候補 ・実験の候補 ・問いに未紐づけの実験

候補から以下の操作ができるようにする。

問い：重点化／編集／統合／解消／破棄
実験：実験中にする／問いへ紐づける／編集／完了／やらない

問いに紐づいていない実験には「問い未設定」という警告ラベルを表示する。

# 整理モード

探求ボード右上に「整理する」ボタンを追加し、問いまたは実験を複数選択可能にする。

問いを複数選択：問いを統合／候補へ戻す／完了／破棄
実験を複数選択：実験を統合／同じ問いへ紐づける／候補へ戻す／完了／やらない

## 問いの統合

複数の問いを選択して「問いを統合」を押すと、統合後の問いを編集できるモーダルを表示する。

表示項目：選択した元の問い／統合後の問い／現在の仮説／テーマ／重点にするか候補にするか

統合後は、新しいQuestionを作成するか、代表となるQuestionを更新する。
元の問いは削除せず、status: "merged"、mergedIntoId: 統合先ID として履歴を残す。
元の問いに紐づく実験・ログ・テーマは、統合先へ引き継ぐ。

# 実験の追加・編集

問いカード内の「実験を追加」から、その問いに紐づいた実験を追加できるようにする。

必須：実験内容
実験中にする場合は必須：使う場面／観察すること／期限
任意：関連テーマ／補足／完了条件

候補として保存する場合は、実験内容だけでも保存可能にする。

# 実験の振り返り

実験中のカードには「振り返る」ボタンを設置する。

入力項目：実際にやったこと／結果／気づき・学び／次回変えること／状態

状態は以下から選択し、Experiment.statusを更新する。

継続 → active ／ 完了 → complete ／ 変更 → changed（または変更後の新実験を作成）
保留 → paused ／ 原則化 → principled

振り返り内容は、可能であれば既存ログにも保存するか、既存ログと相互に参照できるようにする。

# 実践原則

探求ボード内に「実践原則」タブを新設し、カテゴリ別に表示する。

・対話 ・判断 ・組織 ・自分 ・その他

実験の振り返りで「原則化」を選択した場合、実践原則の作成モーダルを表示する。

入力項目：原則名／カテゴリ／説明／元になった実験／元になった問い

例：
原則名：答えを渡す前に、問いを一つ置く
カテゴリ：対話
元になった実験：大樹さんとの1on1で、答えを返さず問いを一つ置く
元になった問い：自分がいなくても構想を広げる人をどう育てるか？

原則は編集・アーカイブ・関連ログ参照ができるようにする。

# ホーム画面変更

ホーム画面では次の順で表示する。

1. VISION
2. 現在の重点
3. 重点テーマ
4. 最近の振り返り

「現在の重点」には重点の問いを最大3件表示し、各問いの下に関連する実験中の実験を表示する。
問いと実験を別セクションに分離せず、必ず問いカードの中に実験を表示する。
問いに紐づかない実験中の実験がある場合は、最後に「問い未設定の実験」として警告表示する。

ホーム画面から以下の操作を可能にする。
・問いの編集 ・実験の追加 ・実験の振り返り ・探求ボードを開く

# 新規追加の動線

新しく作成した問い・実験は、原則として最初はcandidateとして保存する。
登録画面で明示的に「重点にする」「実験中にする」を選んだ場合のみ、focusまたはactiveにする。

新規追加時の選択肢：問いの候補／実験の候補／実践原則の候補

既存のログ入力画面からquestionやnextExpが登録された場合も、
新しいQuestion・Experimentを自動作成する。同じ保存処理内で重複作成しない。

**「⬇取り込む」（---REFLECT-IMPORT--- パーサ経由）で登録される問い・実験も、
同様に新しいQuestion / Experimentとして作成すること。**
旧checks方式にだけ書いて探求ボードに反映されない、という状態を作らない。
壁打ち→取り込み→探求ボード反映、の循環が閉じることが必須。

# 完了画面

探求ボードの「完了」には以下を表示し、フィルターで切り替えられるようにする。

・解消した問い ・統合された問い ・破棄した問い
・完了した実験 ・変更した実験 ・保留した実験 ・やらないと決めた実験

完了項目は、再開・候補へ戻すことができるようにする。

# UIデザイン

現在の以下のデザイン方針を維持する。

・余白を広く取る ・白、生成り、緑を中心とした落ち着いた配色
・角丸や装飾を増やしすぎない ・経営者が毎日使っても疲れない
・文字情報を中心にする ・スマートフォンでも利用可能

ただし、問いと実験の階層が分かるようにする。

推奨：
・問いカード：白背景、通常の枠線
・実験カード：問いカード内で薄い緑または薄いグレー背景
・重点：緑の左線またはラベル ・候補：グレー ・振り返り待ち：薄い黄
・完了：薄い青 ・破棄：薄い赤または低コントラスト

色だけでなく、文字ラベルでも状態が分かるようにする。

# 既存バグの確認

ホーム画面のbuildClSection内で、定義されていない可能性があるqs・expsを参照している箇所がある。

if(theme && !qs.length && !exps.length)

に相当する処理を確認し、ReferenceErrorが起きないように修正する。
判定は、実際に計算した問い・実験の配列を使うか、filtered内に対象データがあるかで行う。
他にも、改修時に未定義変数・古い状態キー・行番号依存の処理が残っていないか確認する。

# JSON保存・読込／バックアップ・brief連携の互換

- JSONエクスポートには、新しいquestions・experiments・principlesデータも含める。
- JSON読込時には、旧形式と新形式の両方を読み込めるようにする。
  旧形式の場合は自動移行する。既存データを上書きする場合は確認ダイアログを表示する。
- **Cowork（Morning Brief）はバックアップJSON内の `reflectOS.activeExperiments` を読み、
  「実験中の実験」を日次提案に使う。ステータス体系変更後も、status=='active' の実験が
  従来と互換の形でエクスポートに含まれること。**
  フィールド名を変えた場合は、エクスポート側で互換キーを維持するか、
  変更内容を完了報告に明記する（Cowork側パッチで追従できるようにする）。
- Task OS側の全OSバックアップ（collectAllOSData）がReflect OSをどう扱っているかを確認し、
  reflectOS_idb 経由の保存・復元で新ストアが失われないことを検証項目に加える。

# 実装上の注意

・既存機能を削除しない ・ログ、テーマ、VISION、Lectica機能を壊さない
・既存IndexedDB／localStorageデータを失わない
・ユーザー入力をinnerHTMLへ直接入れない ・XSSを避ける
・状態変更後は画面とナビゲーション件数を同期する
・同じイベントリスナーを重複登録しない
・旧checks方式に依存する処理を段階的に新データへ置き換える
・移行期間中は旧形式との互換性を維持する
・日付はYYYY-MM-DD形式を維持する ・外部ライブラリは原則追加しない

# 実装順序【3フェーズ・各フェーズでコミット】

一括実装・一括コミットにしない。各フェーズ完了時に動作確認→コミット＆pushする。
途中で壊れた場合に切り戻せる粒度を保つ。
コミットメッセージに「reflect-os: 探求ボード Phase N」を含める。
各フェーズのコミット前に構文検証（node --check / esbuild）を通す（既存運用どおり）。

**Phase 1：**
1. 現在のコードとデータ構造を調査
2. 移行前スナップショット機能を実装
3. IndexedDBに新ストアを追加（DBバージョンアップ・既存ストア保護）
4. 既存データ移行処理を実装（冪等）
5. 探求ボード最小版（重点／候補／完了タブ、3件制限＋入れ替えモーダル、
   問いカード内の実験表示）

**Phase 2：**
6. 統合（merged履歴）・整理モード
7. 実験の追加・振り返り

**Phase 3：**
8. 実践原則タブ
9. ホーム画面変更
10. JSON保存・読込の新形式対応／brief互換確認
11. 旧問い・実験タブを整理／新規動線（ログ入力・取り込み経由）を新構造へ接続
12. スマートフォン表示を調整
13. 動作確認・変更内容を報告

# 受入条件

以下をすべて満たしたら完了。

1. 既存のログ・テーマ・VISION・Lecticaが消えない
2. 既存の問い・実験が新構造へ移行される
3. 問いと実験に独立したIDがある
4. 重点の問いを最大3件に制限できる
5. 実験中を最大3件に制限できる
6. 問いカードの中に関連実験が表示される
7. 複数の問いを統合できる
8. 元の問いが履歴として残る
9. 実験を問いに紐づけられる
10. 実験の振り返りを登録できる
11. 実験から実践原則を作成できる
12. 新しい問い・実験は原則として候補に入る
13. 完了・破棄・統合項目を確認できる
14. JSON保存・読込で新データも復元できる
15. PCとスマートフォンの両方で操作できる
16. JavaScriptコンソールにエラーが出ない
17. ページ再読込後も状態が維持される
18. DBバージョンアップ後、旧データ（ログ・テーマ・Lectica・checks）が1件も消えていない
19. REFLECT-IMPORT取り込みが新構造に反映される
20. status=='active' の実験が従来互換の形でエクスポートに含まれる

# 手動テスト項目

・既存データを保持したまま起動できる
・移行前スナップショットが移行の前に取得される
・旧questionが問い候補として移行される
・旧nextExpが実験候補として移行される
・移行を2回起動しても重複生成されない（冪等）
・問いを重点化できる／4件目の重点化時に入れ替え画面が出る
・実験を実験中にできる／4件目の実験中への変更時に入れ替え画面が出る
・問いに実験を追加できる／未紐づけ実験を問いへ紐づけられる
・問いを2件以上選択して統合できる／統合元の問いが履歴に残る
・実験を振り返り、完了できる／実験から原則を作成できる／原則を編集・アーカイブできる
・REFLECT-IMPORT形式のテキストを取り込むと、問い・実験が候補として探求ボードに現れる
・JSON保存後、読込で復元できる／ページ再読込後もデータが残る
・モバイル幅でレイアウトが崩れない
・既存のLectica取り込みが動作する
・既存のログ追加・編集・削除が動作する

# 作業完了時の報告形式

実装完了後、以下を簡潔に報告する。

1. 変更したファイル
2. 追加したデータ構造（ストア名・DBバージョン）
3. 既存データの移行方法
4. 追加した主要UI
5. 修正したバグ
6. 実施したテスト
7. activeExperimentsのエクスポート形式に変更があればその内容（Cowork追従判断用）
8. 残っている制約・今後の改善候補

不明点があっても、まず既存コードから合理的に判断して実装を進める。
実装を止めるほど重要な前提が不足している場合のみ、質問を1つする。

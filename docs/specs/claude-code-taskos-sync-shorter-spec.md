## §1 経緯（今の `gdAutoSync()`・3185 付近）
Task OS を開くたびに、次を順番に行っている：
1. daily-tasks.json を読む／ヒトメモの連絡先を取り込む／Lectica の Shot を作る
2. 毎朝用のバックアップ `myapps-all-backup.json`（約2.4MB・**字下げ2つで整形**）を書く
3. 週次のバックアップ `myapps-weekly-{ISO週}.json`（全履歴・**字下げつき**）を**毎回**書き、`gdPruneWeekly()` で一覧を取る
4. `inboxFetchFromDrive()`：Drive 10 の直近60日の `import-inbox*` を一覧し、**全部を1本ずつ順にダウンロード**して保留を作り直す
5. 受信箱のハブ（`inboxHubRun`）

受信箱のファイルは1日1〜3本ずつ増える（10/26〜11/10 で約25本）。取り込み済みのファイルも毎回読み直すので、日を追うごとに同期が長くなる。本人決定（11/10）：下の §2〜§6 を全部入れる。**データの中身は変えず、Drive を読む量と書く回数を減らすだけ**

## §2 受信箱：新しいファイルと書き換わったファイルだけ読む（`task-os/index.html`）
- 一覧の `fields` に `modifiedTime` を足す
- 新しい localStorage キー `import_inbox_files_seen_v1`：`{ fileId: { modifiedTime, allDone: true|false } }`
- 一覧の各ファイルについて：
  - 覚えている `modifiedTime` と同じ、かつ `allDone: true` → **ダウンロードしない**
  - それ以外 → ダウンロードして今と同じく読む。読んだあと、そのファイルの有効な item（`id` と `targetOS` がある）が**全部** `import_inbox_done_v1` に入っていれば `allDone: true`、1つでも入っていなければ `false` で覚える（中身が読めないファイルは `allDone: false` のまま。毎回読み直してよい）
- 一覧に無くなったファイル（60日を過ぎた・消えた）は覚えから消す
- 保留の作り直し（`items=[...byId.values()]`）の結果は今と同じになること（読まないファイルは全部取り込み済みなので、保留に入るものが無い）
- 依頼書9 の「取り下げ」で取り込み済みに入った id も、ここで「済み」に数える（同じ `import_inbox_done_v1` を見るので自然にそうなる）

## §3 受信箱：4本ずつまとめて読む
- §2 で読むと決まったファイルのダウンロードを、**同時に4本まで**並べて行う（今は1本ずつ順番）。結果の組み立て（同じ id は `createdAt` が新しいほう）は今と同じ

## §4 週次のバックアップは1日1回
- 新しい localStorage キー `taskos_weekly_uploaded_ymd`（その日の日付 `YYYY-MM-DD`）
- 同期のとき、このキーが今日なら **週次のバックアップの書き込みと `gdPruneWeekly()` を飛ばす**。今日でなければ今までどおり書いて、書けたらキーを今日にする
- **本人が「同期」ボタンを押したとき（`gdAutoSync(true)`）は、今日でも書く**（本人が今の状態を残したいとき用）
- 毎朝用のバックアップ `myapps-all-backup.json` は今までどおり**開くたびに**書く（各担当が読む最新の状態なので）

## §5 バックアップを詰めて書く
- `gdUpload()` に渡す2本（毎朝用・週次）を `JSON.stringify(…)`（字下げなし）にする。中身（キーと値）は今と同じ
- 手動のエクスポート（`myapps-all-backup-YYYY-MM-DD.json` をダウンロードする 954 行付近）は今のまま（字下げつき）
- 読む側：各担当（Cowork）はバックアップを JSON として読んでいるので影響しない

## §6 同期の各段の時間を記録する
- 新しい localStorage キー `taskos_sync_timing_v1`：直近10回分の配列。1回分は
  `{ at: ISO時刻, manual: true|false, totalMs, steps: { dailyTasks, hitomemo, lectica, collect, uploadMorning, uploadWeekly（飛ばしたら "skip"）, inboxList, inboxDownload }, inboxFiles: 一覧の本数, inboxDownloaded: 読んだ本数 }`
- 同期が途中で失敗しても、そこまでの段を記録する
- バックアップ（`collectAllOSDataWithReflect()` の結果）の一番上に **`taskosSyncTiming`** としてこの配列を入れる（メンテナンス担当がバックアップで時間を確かめるため）。バックアップは同期の途中で作るので、入るのは**前回までの**記録でよい
- 画面には出さない（件数・秒数の表示は作らない）

## §7 確かめること・報告の形
確かめること（Code 自身の確認・試しのデータで。`gdFetch`／`gdDownload`／`gdUpload` を数える試しの差し替えでよい）：
1. 受信箱ファイル25本（全部の item が取り込み済み）の試しで、1回目は25本読み、2回目は0本。そのうち1本の `modifiedTime` を変えると、3回目はその1本だけ読む。新しいファイルを1本足すと、その1本だけ読む
2. 取り込み済みでない item を1つ含むファイルは毎回読まれ、その item が今までどおり保留に入る。保留の結果が、直す前の作りと同じ（同じ試しの一覧で比べる）
3. 同時に読むのが4本を超えない
4. 自動の同期を同じ日に2回走らせると、週次のバックアップは1回目だけ書かれる。「同期」ボタン（手動）では2回目でも書かれる。日付が変わると自動でもまた書かれる
5. 書き込む2本が字下げなしで、`JSON.parse` した結果が直す前の整形版と同じ。大きさが何割減ったか
6. `taskos_sync_timing_v1` に直近10回分だけ残り、バックアップの `taskosSyncTiming` に入る
7. 本物の Drive で1回同期した時間（`totalMs`）と、各段の内訳（分かる範囲で。Code の手元で本人のトークンが無ければ、試しの数え上げだけでよい）
